# 后端模块与维护约定

更新：2026-11-13。本文说明当前代码边界，不代表生产容量已经验收。

## 规划主链路

HTTP 路由 → planning_application_service → job_submission_service → planning_job_service → Worker/子进程 → LangGraph → Agent 能力与质量服务。

| 模块                                     | 职责                      | 不负责                 |
| -------------------------------------- | ----------------------- | ------------------- |
| api/routes                             | 参数、响应、HTTP 错误和事件流       | 拼装模型提示词、跨路由调用业务私有函数 |
| planning_application_service           | 规划/修改用例，运行检查、账号配额、服务端记忆 | 消费队列、执行模型           |
| job_submission_service                 | 账号级幂等提交和任务归属            | 生成行程                |
| planning_job_service / planning_worker | 任务状态、排队、消费和重试           | 解释旅游需求              |
| job_process / planning_runner          | 隔离执行、超时、进程退出和租约约束       | HTTP 响应             |
| graphs                                 | 编排研究、生成、确认、修改和降级        | SQLite 连接管理         |
| agents/trip_planner_agent              | 研究、提示词、生成和修复能力          | 公网任务准入、数据库事务        |
| plan_response_parser                   | JSON 清洗、字段归一、模型校验       | 访问地图、生成兜底计划         |
| fallback_plan_service                  | 明确标记的离线参考模板             | 冒充实时查询结果            |
| trip_quality_service                   | 完整计划收尾、增量修改收尾、预算和时间线入口  | 保存行程版本              |
| trip_projection_service                | 历史行程的展示兼容，不回写旧版本        | 实时价格查询、重新生成计划       |
| infrastructure/database                | SQLite 路径、连接、事务提交/回滚、关闭 | 用户认证和旅游规则           |

## 入口与兼容规则

- 新客户端使用 `/api/trip/jobs`、`/revision-jobs` 与 SSE；交互确认通过任务恢复接口继续执行。
- 旧 `/api/trip/plan` 已标记弃用，仍返回原计划响应，但内部复用同一任务提交链，不再直调旧规划器。
- 旧同步请求需要用户确认时返回 409 和任务编号；等待超时返回 504 和任务编号，任务不因此取消。调用方应转用任务查询/恢复接口，而不是反复新建任务。
- 幂等命中不再次扣规划配额；新建任务才加载服务端记忆。客户端提交的记忆上下文不受信任。
- `/api/map`、`/api/poi` 要求登录。旧 `/api/poi/search` 保留响应兼容并标记弃用，新搜索使用 `/api/map/poi`。
- 同步地图/MCP 查询在线程池执行，不直接阻塞异步接口的事件循环。
- 规划健康探针只读取运行状态，不初始化 Agent、不下载依赖。

## 数据库与收尾规则

- 默认数据文件仍为 `backend/data/tripmind.db`，本轮不移动数据库、不执行数据清理或新表迁移。
- 账号、会话、摘要、提醒核验和提交记录共用 `application_database`；不再借认证服务提供通用连接。
- 行程与攻略存储支持注入独立数据库路径，统一复用连接参数和事务实现。所有连接启用外键约束。
- `AuthService.connection()` 是兼容入口，实际仍调用公共数据库层。
- 行程追加版本保留“读取基础版本 → 不持写锁完成计算 → BEGIN IMMEDIATE 再比较版本 → 写入”的原有规则。
- 完整生成使用 `trip_quality_service.finalize`；增量修改使用 `finalize_revision`，只重建受影响日和预算，不做全局景点重排。
- 历史展示兼容与正式写入收尾不是同一个模式，不应为了减少文件而强行合并。

## 缓存规则

- 图片使用公共 SharedCache 的内存层和可选独立 Redis，类型为 `attraction_image`，成功结果有效期 30 天。
- 取消无期限的图片 `lru_cache`；查询失败的 None 不缓存，后续请求可以重新查询。
- 图片缓存遵循 `CACHE_ENABLED`，没有独立缓存 Redis 时只使用有界内存层；不再复用任务 Redis 的旧 `attrimg:` 键。旧键不主动删除，按原期限自然失效。
- 本轮未修改实际环境配置。缓存原本关闭时仍保持关闭。

## 保留边界与后续工作

- Worker、执行器、进程监管职责不同，不合成大文件；会话摘要与长期偏好也保留分工。
- 旧全 JSON 生成和整计划修改仍承担降级能力，不能按“旧代码”直接删除。正式编排通过公共方法调用能力，不再依赖规划器的下划线私有方法。
- 当前仍有分模块建表/兼容迁移，尚未引入统一版本化迁移工具；也未切换 PostgreSQL。
- SQLite/Redis 跨存储发布恢复、正式部署配置和真实多进程压力验收仍按工程计划推进，不能用本轮离线回归替代。

## 验证方式

在后端虚拟环境运行 `scripts/check_offline_suite.py`：临时数据库替代真实业务文件，禁止外部网络并关闭真实模型/地图密钥。新增回归覆盖统一数据库事务、解析器独立使用、服务端记忆注入、旧规划入口复用队列、地图鉴权、图片失败后重试和异步查询线程隔离。

本轮最终结果：273项通过，0失败、0错误；其中新增9项针对模块边界、旧入口完成响应和健康状态检查。不代表真实上游调用或生产并发容量已验收。
